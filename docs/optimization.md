# v0.3.1 优化与验证

日期：2026-11-03。基线为 `b6b80b1`（v0.3.0）。本轮改进默认 CPU 路径的耗时与内存、分散组件查询、CUDA 边界一致性、导出保护及查看器交互。算法的覆盖含义和默认方法不变。实测数据与验证摘要见 [实验快照](optimization-2026-11-03.json)。

检查范围覆盖资产解析与坐标变换、拟合和质量报告、CPU/CUDA 与并行资源、导出/重载、查看器、测试和打包。现有 `load_asset → fit_asset/fit_mesh → write_outputs` 边界清楚，可选运行时继续延迟加载；主要性能问题来自完整细分网格、大型中间数组，以及多组件重复查询全局格点。本轮沿这些边界优化，保留既有方法选择与结果格式。

## CPU 耗时与内存

在同一进程交替测量参考实现和当前实现，预热后各运行 7 次，表中为中位数。参考距离/梯度保留 v0.3 的公式；参考体素化调用 trimesh 原实现；组件查询参考覆盖完整全局栅格。每组先检查输出一致，再计时。

机器为 Ryzen 9 9950X、RTX 5090 D v2，Python 3.10.0、NumPy 1.26.4、SciPy 1.15.3、trimesh 4.12.2。桌面和其他 GPU 程序仍在运行，绝对时间会波动。内存为 `tracemalloc` 记录的数组/对象分配峰值，使用十进制 MB；不是进程 RSS、总显存或第三方原生运行时内存上限。

| CPU 阶段 | v0.3 参考 | v0.3.1 | 倍数 | 分配峰值，参考 → 当前 |
| --- | ---: | ---: | ---: | ---: |
| 距离，6,000 点 × 32 球 | 6.16 ms | 0.87 ms | 7.10× | 4.77 → 1.10 MB |
| 距离，100,000 点 × 32 球 | 82.05 ms | 12.35 ms | 6.64× | 5.52 → 1.85 MB |
| 距离，20,000 点 × 256 球 | 145.90 ms | 14.74 ms | 9.90× | 19.04 → 4.36 MB |
| CPU 梯度，12,000 点 × 128 球 | 36.69 ms | 5.46 ms | 6.72× | 98.30 → 13.80 MB |
| 圆柱表面体素化，res48 | 563.03 ms | 253.21 ms | 2.22× | 348.82 → 15.06 MB |
| 球表面体素化，res80 | 88.31 ms | 40.64 ms | 2.17× | 71.74 → 13.42 MB |
| 27 个分散 box，Open3D CPU 准备 | 12.46 s | 0.166 s | 74.98× | 未计原生内存 |
| 27 个分散 box，Warp CPU 准备 | 4.17 s | 0.078 s | 53.49× | 未计原生内存 |

这些是分阶段数据，不能将倍数当作完整球化的倍数。27 组件案例刻意包含大量组件外部格点，局部包围盒查询因此收益很高；单一实体或高度重叠组件通常没有相同收益。

改动包括：

- CPU 距离使用 SciPy `cdist` 分块计算，省去 `(点, 球, 3)` 差向量及平方临时数组。
- CPU 梯度仅为每个点当前激活的球构造方向，其余点球对只保留距离；优化目标与解析梯度不变。明显超过训练预算的请求在采样前拒绝。
- 默认体素化以有界批次深度优先细分三角形，直接写入布尔表面壳。中点、最大边长、格点舍入和填充规则与参考相同，不保存完整细分网格。
- 可选距离后端只枚举组件包围盒附近格点，保留边界格层、全局格点顺序、数值裕量及组件代表点语义。

复现核心对比：

```bash
python benchmarks/benchmark_hotpaths.py --repeats 7 \
  --geometry-backend open3d --geometry-backend warp \
  --output outputs/benchmark-hotpaths.json
```

没有可选几何运行时时，省略两个 `--geometry-backend` 即可运行 CPU 核心对比。

上述历史表格的体素化参考来自 Trimesh 4.12。为兼容 Trimesh 5 的细分规则变更，当前脚本使用公开 `remesh.subdivide` 构造整轮 1→4 参考；采样规则相同，参考实现的耗时和分配峰值与历史原生实现可能不同。

## CUDA 边界与取舍

扩大验证范围后发现：padding 恰好为半个体素附近时，KD-tree 的平方距离判定与 CUDA 范数的舍入会产生差异。对 `voxel` 测试 4 种形状 × 3 个分辨率 × 3 种 padding × 2 个种子 × 2 种球预算，共 144 组配置、288 次完整拟合，旧实现有 21 组球模型不同。

当前贪心比较平方距离并明确坐标累加顺序，距离报告也使用同样顺序，避免融合范数改变边界符号。极端半径另用归一化判定，避免平方变为零或无穷。144 组的球参数、表面覆盖率和体素覆盖率现均逐项相同；显存工作预算测试通过。这是本机测试结果，不是所有硬件和库版本的逐位一致承诺。

一致性需要额外算术调度。15 次交替热计时中，CUDA 距离的 6,000×32 案例从 0.170 ms 到 0.219 ms，50,000×128 从 0.990 ms 到 1.374 ms；贪心的两个案例约保持原耗时。原地缓冲区复用减少了这项开销。本轮主要加速来自 CPU 和几何准备，没有宣称所有 CUDA 阶段都更快。

## 导出与查看器

- `--force` 也不能覆盖源文件及 URDF 的 mesh/纹理引用；CLI 在拟合前预检已有输出。Python 可调用 `check_output_paths`。
- 导出同时重写 URDF mesh 和 material 纹理路径；未知插件/扩展中的同名元素保持原样。
- GLB 为每 link 共享一个单位球网格，球心和半径保存在节点变换中。遍历实例应使用场景图。G1 的 824 球案例，生成中位时间约从 0.631 s 到 0.062 s，文件从 8.85 MB 到 7.08 MB；全部实例位置和半径可重读。
- 查看器复用几何对象，编辑时只传属性变化；若 Viser 忽略微小坐标变化，仅重建相应单球以保持画面与数据一致。连接时自动取景，`Frame model` 支持全部模型及 solo link。保存使用独立临时目录，并保护源资产。
- 结果 JSON 保持 schema 1，旧配置缺省字段继续使用默认值。损坏结构、无效数值/变换和不合法报告字段会得到 `ValueError`。`Sphere` 不保留调用方可修改的球心数组。

- 15 个单闭合 link 使用相同的独立表面样本和 200,000 个体积样本比较五种结果，种子为 100903。`slab` 的样本内部覆盖率均为 100%，但空心/横向复杂结构的外扩明显；不据此更改默认方法。
- 无界面 Chrome 分别验证双连杆示例和 36-link、824 球 G1 结果：自动取景、选择 link、真实半径输入、指标失效、solo、重新取景、隐藏/显示、保存与重读，未出现 JavaScript 运行时异常。使用软件 WebGL，未测浏览器 GPU 帧率。
- 连续执行 3,000 次 CPU 拟合，包含默认圆柱体素化、球体 refined 和 torus 的 Warp CPU 距离查询；球参数及报告保持确定，输入顶点不变。约 368 秒内的预热后 RSS 读数为 259–267 MB，没有持续增长趋势；这不等于内存泄漏的形式化证明。

上述 15 个 link 的体积评价如下。IoU 是逐 link 的非加权均值，覆盖率列取最小值；每个 link 的五种模型共用评价域，内部有效样本至少 1,044 个。它描述这一批资产与固定预算，不代表通用方法排名。

| 方法 | 平均体积 IoU | 最低样本体积覆盖率 |
| --- | ---: | ---: |
| cover | 0.174 | 96.6% |
| cover-tight | 0.238 | 96.2% |
| slab | 0.217 | 100% |

可见表面包络不等于实体内部覆盖，较高平均 IoU 也不能保证每个 link 都有足够覆盖；空心结构的保守包络可能外扩很大。碰撞模型仍需按实际 link 检查。

源码包和 wheel 可构建。wheel 在源码目录之外运行测试，并在独立虚拟环境（复用宿主依赖）中跑通拟合、报告、五类导出和 JSON 重读。第三方机器人源资产及 mesh 未加入仓库。原生 Lula 和下游规划器碰撞运行仍未进行集成验证。

## 后续精简与热点优化

本阶段以开始时的未提交 v0.3.1 源码快照为基线，具体计时和验证范围见 [后续实验记录](optimization-round2-2026-11-03.json)。保留公开调用与默认方法，没有增加方法注册器或类层级。

- `fit.py` 从 650 行收敛为 264 行，只负责准备、调度和报告。共享采样/距离进入 `geometry.py`，表面与体素实现分别放入 `surface_fit.py`、`voxel_fit.py`；去掉 refine/quality 对调度模块的反向依赖。原有采样、距离函数导入路径保留。
- 最远点选择复用一列平方距离；三角形按稳定顺序分组，避免每簇重复扫描全部标签，并保持原求和顺序。体素候选用布尔掩码排除已有峰值，省去全量去重排序。
- CPU 梯度按激活球索引汇总贡献，减少重复索引写入。质量评价仅在确实需要实体分类时创建体积样本。
- 清晰命名点、球、张量、分块和装配树变量，修正缓冲区复用等注释；保留公开关键字参数。
- 查看器只更新被编辑的球；普通选择只更新新旧高亮，solo 时更新可见性。球心、半径分别编辑，未修改输入不会使质量指标失效。

配对热计时中，最远点选择的 6,000×32、50,000×128 案例分别约快 1.57×、1.62×，分配峰值从 0.34/2.07 MB 降到 0.10/0.80 MB。三种简单形状的完整 `cover` 拟合约快 1.11–1.34×。梯度案例约快 1.01–1.18×，圆柱 24 球、120 步的优化阶段约快 1.05×。这些是指定输入的阶段或方法计时；共享桌面有负载波动，G1 多线程计时中也有变慢案例，不能将局部倍数推广到所有完整拟合。

该阶段完整源码测试 **270 项通过**。27 组 CPU/CUDA 的球参数和报告与阶段基线逐项相同；576 组数值检查中，496 组成功结果和 80 组精度拒绝结果均一致。G1 的 36 个几何 link 用六种方法、两种预算、两个种子完成 24 组配置，每组新旧各运行三次，球参数、报告、导出 JSON 重读均一致。wheel 在源码目录之外通过 54 项拟合、并行及质量测试。

查看器旧值问题来自切换选择时迟到的控件同步消息。现在为每次选择重建两个编辑控件，旧控件事件不能修改当前球。真实 Chrome 的双连杆和 G1 测试确认：控件完成切换后编辑，输入框、模型与保存 JSON 均为 0.045 m；最终 G1 版本另行复验通过。若在新控件出现前输入，旧事件可能被丢弃并提示重试。测试使用软件 WebGL，没有测浏览器 GPU 帧率。

另外试过 CPU 批量邻域查询：两个生产候选案例的耗时收益很小，整批查询的分配峰值约增至原来的五倍，因此保留逐候选查询。

CUDA 也比较了将每步两次标量读取合并为一次主机传输的方案。七个完整贪心案例各做三轮、每轮每方案 31 次交替测量，没有稳定收益，多数略慢，因此同样保留现有实现。

## 加载复用、临时内存与跨版本检查

本阶段参数、原始计时和验证范围见 [第三阶段记录](optimization-round3-2026-11-03.json)。

后续检查新增了单次资产加载的重复 mesh 复用：只缓存所选几何中重复的文件名，每个实例复制后独立应用缩放和位姿，独有文件不额外保留副本。16 个 link 共享约 1 MB STL 的配对加载中位数由 317 ms 降至 35.7 ms，分配峰值由 42.0 MB 降至 24.0 MB；16 份独立 STL 的耗时与峰值基本相同。G1 加载仅有约 1% 的计时差异，不能将共享案例的倍数外推到整台机器人。

细分在生成子三角前释放边长临时数组，终止批次直接复用当前三角数组。八个栅格案例约快 1.00–1.15×，分配峰值少 0.79–1.31 MB；36 组形状、平移、批次组合的表面与填充栅格完全一致。包围球支持点筛选也去掉了全量去重排序，13 组中心、半径与诊断相同；完整函数峰值仍由归一化数组主导，没有下降承诺。改用平面索引抽取外部训练点的实验未显示整体收益，已撤回。

还检查了按球数增大距离查询点块的方案。两套依赖环境的预试均没有稳定收益，100,000 点×32 球案例的分配峰值约由 1.85 MB 增至 5.00 MB，因此保留固定点块。

损坏 OBJ 的正、负越界面索引现在得到含路径的 `ValueError`，CLI 返回 2；缺少依赖与文件系统异常继续保留原语义。该阶段 Python 3.10 全量测试 **277 项通过**。干净的 Python 3.12 / NumPy 2.5.4 / SciPy 1.18.1 / Trimesh 5.2.0 环境为 **220 通过、35 跳过**；Python 3.11 的可选几何环境为 **246 通过、5 跳过**。跳过项对应未安装的可选运行时或缺少执行条件。

跨版本检查发现 Trimesh 5 改为逐长边细分。相同输入中，旧规则和本项目流式实现跨环境均为 12/12 格点相同，而原生 Trimesh 默认结果只有 1/12 相同。测试和基准改用公开 `remesh.subdivide` 构造独立的全量旧规则参考；保留全部形状、平移和填充检查，也保留原有默认格点。`cover` 使用依赖库的细分器，其球分组仍可能随 Trimesh 版本变化；复现实验需要记录依赖版本。

## 优化器、序列化与操作顺序

参数、配对原始计时和验证环境见 [第四阶段记录](optimization-round4-2026-11-03.json)。

CPU 优化器复用首次计算的梯度，减少一次重复求值；每次更新后仍检查最优状态，包括最后一步。梯度方向只为导数非零的样本计算，完整损失和半径正则项保持原样，并提前释放密集距离工作区。24 组形状、球数与步数组合的完整输出相同。另用 31 次交替配对、单线程数值库复测 120 步优化：四种常见形状约快 1.19–1.24×，G1 髋部约快 1.18×，128 球较大案例约快 1.09×。这些计时包含训练采样和优化，使用相同的预计算初始化；共享主机未保留专用 CPU，不能外推到所有输入。

序列化检查修复了 NumPy 资产缩放、报告指标及变换通过验证后仍不能导出的问题：仅将已验证字段保存为原生数值和列表，不递归转换任意扩展报告。原生数值走较短的有限值检查路径，球导出直接使用构造时保证的不可变值。示例和 G1 的完整 JSON 读取配对中位数约快 1.18× 和 1.11×；额外的 JSON 浮点解析检查本身有开销，作用是拒绝 `1e999` 等会溢出为无穷大的字面量。

查看器用控件绑定的 link/index 处理编辑，选择回调尚未完成时提示重新编辑，避免修改其他球。编辑回调在 Viser 事件循环中完成后再分派后续保存，选择和文件保存继续使用普通回调。真实处理器的 1,000 组按序编辑/保存均得到相同的模型值与文件值；示例和 G1 的浏览器流程通过。一次较大视口的 G1 尝试在选择同步阶段超时，记录诊断后重试通过，没有据此承诺浏览器响应时限。保存序列化失败也会显示错误并保留原文件。

最低声明依赖的完整测试发现 `defusedxml 0.7.0` 的 `ParseError` 与标准库同名类型不同，现于 URDF 解析边界显式兼容。当前完整环境为 294 通过；干净 Python 3.12 为 237 通过、35 跳过；Python 3.11 几何环境为 259 通过、5 跳过；最低依赖为 224 通过、40 跳过，带一条 SLSQP 试探步裁剪警告。CI 增加最低依赖任务，未触发远程执行。

wheel 的 20 个源码模块逐字节对应本阶段源码，在源码目录之外通过 173 项测试、跳过 1 项 CUDA 测试；实际命令行入口完成 refined 拟合、五类文件导出与报告 JSON 重读。

## Slab 临时数组与实体参考说明
